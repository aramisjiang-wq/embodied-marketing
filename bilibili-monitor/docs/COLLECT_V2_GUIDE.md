# B站竞品数据采集系统 v2.0 使用说明

## 🎯 系统概述

这是一个**无需代理IP池**的稳定B站数据采集方案，基于以下核心技术：

- **bilibili-api-python**: 成熟的B站API库（3400+ GitHub Stars）
- **curl_cffi**: 浏览器TLS指纹伪装，避免被识别为爬虫
- **智能频率控制**: 随机延迟 + 指数退避重试机制
- **完善日志系统**: 详细记录每次采集过程

## ✨ 核心优势

### 1. **安全性高**
- ❌ 不需要第三方代理服务
- ✅ 数据不经过未知服务器
- ✅ 完全本地运行

### 2. **稳定性强**
- ✅ 浏览器指纹伪装（chrome131）
- ✅ 自动错误重试（最多3次）
- ✅ 智能频率控制（随机3-6秒延迟）
- ✅ 指数退避策略（避免触发风控）

### 3. **易于监控**
- ✅ 控制台实时日志输出
- ✅ 文件日志持久化存储（`logs/collect.log`）
- ✅ 数据库运行记录表（`run_logs`）

## ⚙️ 配置说明

在 [collect.py](scripts/collect.py) 文件中，您可以调整以下参数：

```python
CONFIG = {
    "base_delay": 3.0,           # 基础延迟（秒）- 增大可降低风控风险
    "random_delay_range": 3.0,   # 随机延迟范围（秒）- 增大可提高稳定性
    "max_retries": 3,            # 最大重试次数 - 建议保持3次
    "page_delay": 1.5,           # 分页请求延迟（秒）
    "video_detail_delay": 1.0,   # 视频详情请求延迟（秒）
    "brand_delay": 2.0,          # 品牌间延迟（秒）- 增大可避免连续请求
}
```

### 推荐配置场景

#### 场景1：追求稳定性（推荐用于生产环境）
```python
CONFIG = {
    "base_delay": 5.0,           # 更长的延迟
    "random_delay_range": 5.0,
    "max_retries": 5,            # 更多重试
}
```
**预计时间**：50个品牌约需 **15-20 分钟**

#### 场景2：追求速度（测试环境使用）
```python
CONFIG = {
    "base_delay": 1.5,           # 较短的延迟
    "random_delay_range": 2.0,
    "max_retries": 2,
}
```
**预计时间**：50个品牌约需 **5-8 分钟**

⚠️ **注意**：过快的速度可能触发B站风控！

## 📊 监控与调试

### 1. 日志文件位置

- **控制台输出**：实时显示在终端
- **文件日志**：`bilibili-monitor/scripts/logs/collect.log`
- **数据库记录**：`run_logs` 表

### 2. 常见问题排查

#### 问题1：频繁出现412/403错误
**原因**：请求频率过快或被识别为异常行为
**解决方案**：
1. 增大 `base_delay` 和 `random_delay_range` 的值
2. 减少同时运行的任务数量
3. 检查是否有其他程序也在访问B站

#### 问题2：某个品牌始终失败
**原因**：该UP主可能设置了隐私保护或账号异常
**解决方案**：
1. 手动访问该UP主主页确认是否正常
2. 在数据库中暂时禁用该品牌：
   ```sql
   UPDATE brands SET is_active = 0 WHERE mid = '问题MID';
   ```

#### 问题3：视频详情获取失败
**原因**：网络波动或临时风控
**解决方案**：
1. 查看 `logs/collect.log` 中的详细错误信息
2. 系统会自动重试3次，通常可以恢复
3. 如果持续失败，可能是该视频被删除或设为私有

### 3. 性能统计查询

```sql
-- 查看最近10次运行记录
SELECT 
    run_time,
    ROUND(duration / 60, 1) as duration_minutes,
    total_brands,
    success_count,
    failed_count,
    total_videos
FROM run_logs 
ORDER BY run_time DESC 
LIMIT 10;

-- 计算成功率
SELECT 
    COUNT(*) as total_runs,
    SUM(CASE WHEN failed_count = 0 THEN 1 ELSE 0 END) as perfect_runs,
    ROUND(AVG(success_count * 1.0 / total_brands * 100), 1) as avg_success_rate
FROM run_logs;
```

## 🔧 定时任务设置（可选）

如果您希望自动定期执行采集，可以使用 `cron`（Linux/macOS）或任务计划程序（Windows）。

### macOS/Linux 设置定时任务

```bash
# 编辑crontab
crontab -e

# 添加以下行（每天早上8点执行一次）
0 8 * * * cd /path/to/bilibili-monitor/scripts && python collect.py >> logs/cron.log 2>&1

# 或者每6小时执行一次（适合需要更频繁更新的场景）
0 */6 * * * cd /path/to/bilibili-monitor/scripts && python collect.py >> logs/cron.log 2>&1
```

### Windows 任务计划程序

1. 打开"任务计划程序"
2. 创建基本任务
3. 设置触发器（例如每天8:00）
4. 操作设置为"启动程序"
5. 程序路径：`python.exe`
6. 参数：`C:\path\to\bilibili-monitor\scripts\collect.py`
7. 起始位置：`C:\path\to\bilibili-monitor\scripts`

## 💡 最佳实践建议

### 1. 分层更新策略

根据您的业务需求，建议采用分层更新策略：

| 数据类型 | 更新频率 | 原因 |
|---------|---------|------|
| **粉丝数/关注数** | 每6小时 | 变化较慢，但重要 |
| **视频列表** | 每天 | 新视频发布频率中等 |
| **视频播放量** | 每周 | 播放量增长相对缓慢 |

### 2. 错峰执行

- **推荐时间**：凌晨 2:00-6:00 或中午 12:00-14:00
- **避开时段**：晚上 19:00-23:00（用户活跃高峰）

### 3. 数据备份

定期备份数据库文件：
```bash
# 创建备份脚本 backup.sh
#!/bin/bash
BACKUP_DIR="/path/to/backups"
DATE=$(date +%Y%m%d_%H%M%S)
cp bilibili_monitor.db "$BACKUP_DIR/bilibili_monitor_$DATE.db"

# 删除30天前的备份
find $BACKUP_DIR -name "*.db" -mtime +30 -delete
```

## 🛠️ 故障排除指南

### 常见错误代码

| 错误码 | 含义 | 解决方案 |
|--------|------|----------|
| **412** | 请求头验证失败 | 检查curl_cffi是否正确安装和配置 |
| **403** | IP被临时封禁 | 增加延迟时间，等待1-2小时后重试 |
| **-352** | 风控校验失败 | 降低请求频率，检查User-Agent等请求头 |
| **ConnectionError** | 网络连接失败 | 检查网络连接，稍后自动重试 |

### 紧急恢复步骤

如果遇到严重问题：

1. **停止当前任务**：按 `Ctrl+C` 中断程序
2. **查看日志**：`tail -100 logs/collect.log`
3. **分析错误**：根据错误信息调整配置
4. **重新运行**：`python collect.py`
