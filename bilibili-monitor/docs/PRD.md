## 1. 产品概述

### 1.1 产品名称
**B站竞品监控系统** - 机器人品牌B站矩阵监控工具

### 1.2 产品定位
面向机器人公司市场部的内部数据分析工具，用于监控竞品在B站的官方账号矩阵表现。

### 1.3 核心价值
- 实时掌握竞品B站声量
- 分析竞品内容策略
- 指导市场投放决策
- **自动化数据采集**（v2.6.0新增）
- **可视化系统运作**（v2.6.0新增）

## 7. 认证与权限管理需求 (v2.31.0 新增)

> ⚠️ **核心架构决策：单产品 + 角色权限模式**

### 7.1 架构设计原则

#### **关键问题：管理员和用户的关系**

| 问题 | 答案 |
|-----|------|
| **管理员和用户在同一张表吗？** | ✅ **是的**，都在 `users` 表，通过 `role` 字段区分 |
| **是2个独立产品吗？** | ❌ **不是**，是 **1个 Next.js 应用 + 3种角色权限** |
| **数据是同一套吗？** | ✅ **是的**，`brands/videos` 业务数据完全共享 |
| **代码是同一套吗？** | ✅ **是的**，只是根据 role 动态显示不同UI |

#### **架构类比**

```
🏢 公司门禁系统（1栋楼）

├── 大门（统一入口）        ← 飞书扫码登录 (/login)
│   所有人刷卡进入
│
├── 1楼：开放办公区        ← 用户端 Dashboard (/)
│   所有员工都能进
│   能看数据、做分析
│
├── 2楼：部门办公室        ← 编辑者权限
│   editor 角色能进
│   能编辑品牌数据
│
└── 3楼：IT机房            ← 管理端 Admin Panel (/admin)
    只有 admin 能进
    能管理系统配置、管理用户

✅ 1栋楼（1个应用）
✅ 同一张工卡（1张 users 表）
✅ 不同楼层不同权限（role 控制）
```

### 7.2 认证系统需求

#### 7.2.1 登录方式

| 属性 | 说明 |
|------|------|
| **认证协议** | OAuth 2.0 标准流程 |
| **身份提供商** | 飞书开放平台 |
| **登录方式** | 扫码登录（飞书 APP） |
| **回调地址** | `/api/auth/callback` |
| **Session有效期** | 7天（HttpOnly Cookie） |

#### 7.2.2 登录流程

```
1. 用户访问任意页面 → Middleware 检查 Session
   ↓ 未登录
2. 自动跳转到 /login 页面
   ↓
3. 显示专业登录页（渐变背景 + 飞书二维码）
   ↓
4. 用户打开飞书 APP → 扫描二维码
   ↓
5. 手机确认授权 → 飞书重定向到 /api/auth/callback?code=xxx
   ↓
6. 后端用 code 换取 access_token → 获取用户信息
   ↓
7. 查找或创建本地用户记录 → 写入 users 表
   ↓
8. 创建 HttpOnly Session Cookie（包含 id + role + status）
   ↓
9. 重定向到 Dashboard（或原访问页面）
```

#### 7.2.3 登录页设计要求

- ✨ 专业视觉设计（渐变蓝灰背景 + 白色卡片 + 飞书品牌色）
- ✨ 实时状态反馈（加载中 → 二维码就绪 → 扫码中 → 成功跳转）
- ✨ 错误友好提示（授权失败显示原因 + 重试按钮）
- ✨ 安全徽章展示（"安全登录 · 飞书账号授权"）
- ✨ 使用指引（3步操作说明）
- ✨ 响应式布局（移动端适配）

### 7.3 用户管理体系需求

#### 7.3.1 数据模型

**单表存储设计**：

```sql
CREATE TABLE users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,  -- 本地用户ID
  open_id TEXT UNIQUE NOT NULL,           -- 飞书唯一标识
  union_id TEXT,                         -- 飞书联合标识
  name TEXT NOT NULL,                     -- 姓名
  email TEXT,                            -- 工作邮箱
  avatar_url TEXT,                       -- 头像URL
  
  role TEXT DEFAULT 'viewer',            -- 角色（见下方定义）
  status TEXT DEFAULT 'active',          -- 状态（active/disabled）
  
  last_login_at TIMESTAMP,               -- 最后登录时间
  login_count INTEGER DEFAULT 0,         -- 累计登录次数
  
  created_at TIMESTAMP,
  updated_at TIMESTAMP
);
```

**为什么不用两张表（admin_users + normal_users）？**
- ❌ 两张表需要维护两套 CRUD 逻辑
- ❌ 角色变更需要跨表迁移数据
- ❌ 查询"所有用户"需要 UNION 操作
- ✅ 单表+字段更简单、更灵活、更易维护

#### 7.3.3 特殊规则

**自动提升规则**：
- 第一个扫码登录的用户 → 自动成为 `admin`
- 后续新用户 → 默认为 `viewer`
- 确保系统至少有一个管理员

**自我保护机制**：
- 不能删除自己的账号
- 不能修改自己的角色（防止锁死自己）
- 至少保留一个 admin 账号（建议2个以上）

**状态控制**：
- `active` 状态 → 可以正常登录
- `disabled` 状态 → 登录时提示"账号已被禁用"
- 用于员工离职、账号冻结等场景

### 7.6 安全特性需求

#### 7.6.1 多层防护体系

```
第1层：Middleware（网络层）
  ↓ 拦截未认证请求，强制跳转登录

第2层：Session Cookie（会话层）
  ↓ HttpOnly防XSS，Secure防窃听，SameSite防CSRF

第3层：Role Check（业务层）
  ↓ API接口验证调用者角色，非admin返回403

第4层：Database Constraint（数据层）
  ↓ SQL CHECK约束确保role/status值合法
```

#### 7.6.2 具体安全措施

| 安全措施 | 实现方式 | 防护目标 |
|---------|---------|---------|
| **HttpOnly Cookie** | `httpOnly: true` | 防 JavaScript 窃取 Session |
| **Secure Flag** | 生产环境自动启用 | 防明文传输被截获 |
| **SameSite=Lax** | 防跨站请求伪造 | 防 CSRF 攻击 |
| **Session 过期** | 7天有效期 + expires_at 校验 | 防长期未失效的 Session 被滥用 |
| **IP 记录** | 登录时记录 x-forwarded-for | 异常登录检测 |
| **User-Agent 记录** | 登录时记录浏览器指纹 | 辅助判断是否为本人 |
| **角色隔离** | API 层统一校验 role === 'admin' | 防越权访问管理接口 |
| **自我保护** | 不允许修改/删除自己 | 防误操作导致锁定 |
| **状态检查** | disabled 用户拒绝登录 | 快速封禁账号 |

## 10. 风险和依赖

### 9.1 技术风险
- B站接口变更可能导致数据采集失败
- 风控策略可能导致IP被封
- 数据量增长可能影响性能

### 9.2 缓解措施
- 定期更新采集脚本适配接口变化
- 使用curl_cffi模拟浏览器降低封禁风险
- 设计可扩展的数据库架构

### 9.3 依赖项
- B站开放平台API稳定性
- bilibili-api-python库维护状态
- 网络环境稳定性
